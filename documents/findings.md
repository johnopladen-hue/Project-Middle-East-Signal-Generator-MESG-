# Findings & Lessons Learned — Project MESG

> Record what we learn during development that isn't obvious from the code itself: dead ends, surprising constraints, things that worked better/worse than expected, corroboration techniques that proved useful or unreliable, etc. This is not a bug tracker — it's institutional memory.

## Format

For each entry:

- **Date:**
- **Context:** What we were doing when we learned this.
- **Finding:** What we learned.
- **Implication:** How it should change future decisions/approach.

- **Date:** 2026-08-02
- **Context:** Filing the Planner's session close-out (`documents/sessions/MESG-close-out-2026-08-02.md`) into the repo. The close-out states, as "repo state as visible to Planner (ground truth)," that a file `Languages_and_Religions.md` is currently visible in the connected repository.
- **Finding:** That file does not exist anywhere in this repo's git history (checked full log across all commits). It does exist locally in the user's Downloads folder, unconnected to the repo. So Planner asserted something as directly-observed repo ground truth that it could not actually have observed via the repo connection.
- **Implication:** Don't take a Planner (or any AI) claim of "I can see X in the repo" at face value — this is exactly the Keel Principle 8 failure mode ("a summary is not knowing"). Verify repo-state claims against the actual repo before acting on them. Practically: confirm whether the Planner project has a separate uploaded-file knowledge source distinct from the connected-repo view, since that's the likely source of the confusion.

- **Date:** 2026-09-06
- **Context:** Conducting the Keel Principle 6/9 "prove the gate" demo for real on this repo (D-007, Keel v9), after discovering the repo's branch ruleset (set up 2026-08-30) only had a "require pull request" rule — no CI workflow and no required status check existed yet, so nothing actually gated on green.
- **Finding:** Laid a minimal self-contained pytest CI workflow (`.github/workflows/ci.yml`, `keel_proof.py`/`test_keel_proof.py`) and added a `required_status_checks` rule (context `test`) to the existing ruleset via `gh api`. Then witnessed all 5 moves for real on PR #4: a deliberately broken test failed CI and left the PR `mergeable_state: "blocked"`; a plain `gh pr merge` was refused ("the base branch policy prohibits the merge") even though the account merging is the repo owner; fixing the test turned CI green and the merge went through; the `deploy` job (currently a placeholder, since the hosting platform is still an open decision) ran immediately after. Separately, the Claude Code auto-mode permission classifier itself blocked an attempted `gh pr merge --admin` override — a second, independent layer refusing the bypass attempt.
- **Implication:** "Require a pull request" alone is not a merge-on-green gate — it only proves Principle 9's "require a PR" half; Principle 6 (prove it by tripping it) requires an actual required status check wired to CI, which has to be verified explicitly rather than assumed present once *any* ruleset exists. Re-check this pairing (ruleset rule types + `gh api .../rulesets/<id>`) any time a new required check is added to CI, since adding a workflow does not retroactively make GitHub require it.

- **Date:** 2026-09-06
- **Context:** Building Order 7 (Story detail, `backend/app/routers/stories.py`). `Analysis` (TDD §6) has no stored column for whether a grade is corroborated — `probability_grade` is stored already-capped by `grading.py`, but the boolean itself isn't persisted.
- **Finding:** Derived `has_corroborating_artefact` as `probability_grade >= 4` for the API response, since the grading cap guarantees nothing above 3 is ever stored without an artefact. This direction is sound, but it's not reversible: a grade of 1-3 could mean either "genuinely doubtful/contradicted" or "merely uncorroborated," and the derived flag can't tell them apart, so `GradeBlock`'s "why" text may say "ceiling without corroboration" for a story that was actually graded low for contradicting evidence, not lack of sourcing.
- **Implication:** This is a real schema gap, not just a UI nuance — once the analysis engine is real (pending the analysis/LLM provider decision), `Analysis` should get an explicit persisted `has_corroborating_artefact` (or equivalent) column so this stops being inferred. Don't extend the `>=4` heuristic further (e.g. into alerting logic) without fixing this first.

- **Date:** 2026-09-06
- **Context:** Order 11's accessibility pass (UI-spec §5.5, "WCAG AA contrast... non-negotiable"). Computed actual WCAG relative-luminance/contrast ratios for the grade-scale palette (§3.2) by hand, then wrote `frontend/src/test/contrast.test.js` to check the math programmatically.
- **Finding:** The palette specified in the UI-spec itself doesn't meet its own accessibility floor when used as literally described. `Badge`, `ImminentPill`, `PipelineStatusStrip`, and the Admin Sources silence flag all rendered `text-grade-N` (colored text) directly — either on that grade's own light (15%) tint, or on the plain surface — for grades 2, 3, and 4 that measured 2.4:1, 3.4:1, and 2.6-3.0:1 respectively (need 4.5:1); grade 5 was borderline at 4.3:1. Only grade 1 (the darkest hue) happened to pass. This had been sitting in the UI since Orders 2, 4, 5, and 10 without anyone (human or AI) checking the actual math — it read as "fine" by eye during each order's own review.
- **Implication:** "The palette is specified in an authoritative design document" is not evidence the palette is accessible — measure it. For any future palette or token addition, run the contrast check (`frontend/src/test/contrast.js`) before deciding a color pairing is usable as text, not after. The fix (text stays `ink`; the grade hue lives only in a background tint or an icon) generalizes to any new grade/severity-colored UI added later — colored text on a tint of the same hue is exactly the pattern that fails.

- **Date:** 2026-09-13
- **Context:** Same first-article session, choosing severity values for the synthetic seed's `Signal.severity` field.
- **Finding:** `backend/app/signals.py`'s `severity_for()` emits `"high"`, `"medium"`, or `"none"`, but the frontend's `SeverityMark` (`frontend/src/domain/SeverityMark.jsx`) and the `Alerts` filter (`frontend/src/routes/Alerts.jsx`) only recognize `"critical"`, `"high"`, `"elevated"`, `"info"` — `SeverityMark` silently falls back to the generic "Info" styling for any value it doesn't recognize (`SEVERITY_CONFIG[severity] ?? SEVERITY_CONFIG.info`), so `"medium"` and `"none"` from the real classifier would both render as unstyled "Info" today. The seed script used the frontend's vocabulary directly to get correctly-styled screens; it did not fix the classifier.
- **Implication:** This is a real, pre-existing contract mismatch between the backend event classifier and the frontend severity display, invisible until something actually populated a Signal end-to-end (no prior order had). It's silent (a fallback, not a crash), which is exactly the kind of gap that survives until real data exposes it. Fix by aligning `severity_for()`'s return values to `SeverityMark`'s four-value vocabulary (or vice versa) when the classifier is next touched — do not seed or test against `"medium"`/`"none"` as if they render correctly.

- **Date:** 2026-09-13
- **Context:** O-4 license gate (D-013/[D-012](decisions/D-012-actor-network-layer.md)) — re-confirming UCDP's current terms against the live source before any harvest, per the actor-network-layer orders. The orders' own text assumed the Actor Dataset (name history, splits, alliances) would be pulled "via the official UCDP API."
- **Finding:** That assumption doesn't hold. `https://ucdp.uu.se/apidocs/` documents the JSON API's actual resources — `gedevents`, `ucdpprioconflict`, `dyadic`, `nonstate`, `onesided`, `battledeaths`, `organizedviolencecy` — and there is no dedicated Actor endpoint; the API also requires a registered `x-ucdp-access-token` (a credential). The Actor Dataset itself is instead a plain public download: `https://ucdp.uu.se/downloads/actor/ucdp-actor-261-csv.zip` (verified reachable with no auth, `curl` → HTTP 200, v26.1, 1990 CSV rows). License confirmed live at `https://ucdp.uu.se/downloads/`: **CC BY 4.0**, redistribution permitted with attribution — required citation: "Shawn Davies, Therese Pettersson, Magnus Oberg, Organized violence 1989-2025, and violent political protests, Journal of Peace Research, 2026," plus a note that MESG's normalized form is not produced by UCDP. ACLED's AI/LLM-training and substitute-product prohibition, and GTD's closed/registration-gated access limited to data through 2020, were both independently re-confirmed live, matching D-013's original text.
- **Implication:** [D-013](decisions/D-013-source-licensing-posture.md)'s UCDP line is corrected to say "downloadable CC BY 4.0 file" rather than "via the official API" — the license/attribution posture is unchanged, but the *mechanism* is a CSV harvester (`backend/app/actors/harvesters/ucdp.py`), not an API client, and needs no credential. This is a better outcome than the orders anticipated (no token to obtain, no Owner credential-handling decision needed for this source) but is exactly the kind of drift Standing Order 1 exists to catch — a snapshot's plan for *how* to harvest a licensed source can be wrong even when the license itself is right.

- **Date:** 2026-09-13

Spot-checked against independently-known public history (not just the file's own label): UCDP's data correctly shows PFLP-GC (id 206) split from PFLP (id 205), and PFLP itself split from two predecessors (ids 204 and 1067) — both real, independently documented facts about Palestinian faction history, not artifacts of this file alone.
- **Implication:** The register now holds real, sourced, licensed actor data for v1 scope, with every row traceable to UCDP's Actor Dataset v26.1 and carrying its required citation. The 24 unresolved-edge count is expected, not a bug — those edges name real UCDP actors (e.g. global or non-regional factions) that fall outside D-008's scope; widening scope later would resolve some of them, which is itself a useful signal for a future scope-widening decision.

- **Date:** 2026-09-13
- **Context:** O-7 — harvesting the real OFAC SDN list (downloaded live, no auth needed: `https://www.treasury.gov/ofac/downloads/sdn.csv` redirects to `sanctionslistservice.ofac.treas.gov`, HTTP 200, 19,388 rows) into `Designation` records, identity-matched against the 123 real organizations from the UCDP harvest above. Note: the US State Department's own FTO list page (`state.gov/foreign-terrorist-organizations`) returned HTTP 403 to both `WebFetch` and a direct `curl` with a browser user-agent — blocked by the site's own bot protection in this environment. O-7 proceeded with OFAC's SDN list (also carries an FTO tag per-entry) rather than scraping past that block; the standalone State Department page is not harvested this session.
- **Finding:** The harvester correctly filtered 19,388 raw rows down to **1,356** organization-level (not individual/vessel) rows under a terrorism-related program tag (`SDGT`/`SDT`/`FTO`). Matching those 1,356 real designation names against our 123 real organizations by whole-string `difflib.SequenceMatcher` ratio at an initial threshold of **0.6** produced 88 "matches" - but manual inspection showed most were false positives at real scale: e.g. `"NATIONAL IRANIAN OIL COMPANY"` matched an unrelated militant faction, `"AL-MUSTAFA INTERNATIONAL UNIVERSITY"` and `"SHAHED PHARM"` likewise, on nothing more than shared generic tokens ("Islamic," "Iran," "Front"). Raising the threshold to **0.85** cut this to **8 matches**, every one spot-checked and confirmed genuinely correct: Hamas, PFLP, PFLP-GC, Al-Aqsa Martyrs Brigade, PJAK ("Free Life Party of Kurdistan"), Jaish al-Adl, Jaish al-Muhajireen wal-Ansar, and Liwa al-Aqsa (matched via its own tracked former name, "Jund al-Aqsa" - a real historical rename UCDP's `NameChange`/alias data had already captured, not a coincidence). The remaining 1,348 designations are stored `unmatched_pending_match`, not dropped. `reconcile()` still shows zero orphan relationships after this second harvest.
- **Implication:** A 0.6 similarity threshold is not safe for this kind of identity matching at real scale — the failure mode (silently attaching a real terrorism designation to the wrong real organization) is a genuine harm this project exists to avoid, not a cosmetic test issue. `MATCH_THRESHOLD = 0.85` in `backend/app/actors/matching.py` trades recall for precision on purpose: a real partial match below that line (this session's own PIJ example, "Palestinian Islamic Jihad" vs. OFAC's "Palestine Islamic Jihad - Shaqaqi Faction," ratio 0.667) is left unmatched-pending-match rather than auto-matched - which is the correct, safe behavior for an uncertain match, not a bug to fix later. Anyone tuning this threshold in the future should re-run against real data at real scale before trusting a lower cutoff, exactly as this session did.
